# E-Commerce Platform — Master PostgreSQL Database Design Prompt

## 1. Project Overview

I am building a modern full-stack e-commerce platform specializing in the sale of:

* Sneakers
* Shirts
* Wrist Watches
* Spectacles

The platform will have a customer-facing storefront and an administrative dashboard.

The system must support:

* Customer registration and authentication
* Product browsing
* Product categories and subcategories
* Product search
* Product filtering and sorting
* Product variants
* Product images
* Product-specific attributes
* Size and color selection
* Shopping cart
* Wishlist

* Customer addresses
* Orders

* Payments

* Product reviews and ratings
* Inventory management
* Inventory history
* Admin users and roles
* Role-based access control
* Audit logs
* Product management

The application will use **Clerk for authentication and identity management**.

The application database must be **PostgreSQL**.

# 2. Core Architecture Principle

Use the following separation of responsibilities:

### Clerk

Clerk is responsible for:

* Authentication
* User identity
* Sign-up
* Sign-in
* Password management
* Email verification
* Social/OAuth authentication
* MFA
* Authentication sessions
* Authentication tokens

Do NOT duplicate these responsibilities in PostgreSQL.

Do NOT create:

* password
* password_hash
* login_token
* session_token
* authentication_token

columns in the PostgreSQL database.

### PostgreSQL

PostgreSQL is responsible for all application/business data, including:

* Customer application profile
* Addresses
* Products
* Categories
* Brands
* Product variants
* Product images
* Product attributes
* Inventory
* Shopping carts
* Wishlists
* Orders
* Order items
* Payments metadata
* Shipments
* Reviews
* Coupons
* Admin roles
* Permissions
* Audit logs

The PostgreSQL database is the **source of truth for commerce/business data**.

# 3. Clerk Integration

Create a `customers` table that maps the Clerk user to the application's customer record.

The table must contain:

```text
id
clerk_user_id
first_name
last_name
phone
date_of_birth
avatar_url
status
created_at
updated_at
```

`clerk_user_id` must be:

* NOT NULL
* UNIQUE
* indexed

The application should use `clerk_user_id` to associate an authenticated Clerk user with their PostgreSQL customer record.

Do not store the user's password or authentication session in PostgreSQL.

The application should be designed so that if a Clerk user is deleted, the corresponding application customer record can be handled appropriately.

Consider webhook synchronization from Clerk for:

* user.created
* user.updated
* user.deleted

Do not blindly duplicate every piece of Clerk user data into PostgreSQL. Store only application-specific information required by the store.

# 4. Database Design Principles

Use a normalized relational design.

Prefer:

* UUID primary keys
* Foreign keys
* Explicit relationships
* Appropriate indexes
* `NOT NULL` where appropriate
* `UNIQUE` constraints
* `CHECK` constraints
* Proper cascading/restrictive delete behavior
* `TIMESTAMPTZ` for timestamps
* `NUMERIC(12,2)` for monetary values
* `JSONB` only where flexible/semi-structured data is genuinely useful

Avoid:

* Storing multiple values in comma-separated strings
* Repeating customer/product information unnecessarily
* Storing images directly as binary data in normal product records
* Storing passwords
* Using floating-point types for money
* Creating separate product tables for sneakers, shirts, watches, and spectacles

Use one unified product system.

# 38. Delete Rules

Use deliberate foreign-key deletion behavior.

Do not use `ON DELETE CASCADE` everywhere.

Recommended principles:

### Customer

If a customer account is deleted, carefully preserve historical orders where required.

Orders should generally not disappear simply because a customer account is deleted.

### Products

Do not allow deletion of a product that is referenced by historical order data unless the relationship has been designed to preserve the historical order.

Prefer soft deletion/archive for products.

### Categories

Prevent deletion where products still depend on the category, or implement a controlled reassignment process.

### Orders

Do not cascade-delete order items, payments, shipments, or status history accidentally.

Orders are historical business records.

### Cart

Cart items may be safely cascade-deleted when a cart is permanently removed.

### Wishlist

Wishlist items can cascade-delete with the wishlist.

### Reviews

Review images can cascade-delete with the review.

Document every `ON DELETE` behavior.

# 40. Money and Currency

Use:

```text
NUMERIC(12,2)
```

for monetary values.

Do not use:

```text
FLOAT
REAL
DOUBLE PRECISION
```

for financial amounts.

Store the currency code using:

```text
CHAR(3)
```

Default currency:

```text
GHS
```

The system should remain capable of supporting other currencies in the future.

# 41. Timestamps

Use:

```text
TIMESTAMPTZ
```

for timestamps.

Default creation/update timestamps appropriately.

The system should store timestamps consistently in UTC and convert them to the user's local timezone at the application/UI level.

# 42. UUIDs

Use PostgreSQL UUIDs for primary keys.

Prefer UUID generation using PostgreSQL-supported UUID functions/extensions appropriate to the deployed PostgreSQL version.

Do not use predictable sequential integer IDs for externally exposed entities unless there is a specific reason.

# 43. Slugs

Products, categories, and brands should have unique slugs.

Example:

```text

```

becomes:

```text
nike-air-max-270
```

Slugs must be indexed and unique.

# 45. Product Rating

Do not necessarily store a permanently duplicated rating total on the product table initially.

Ratings can be calculated from reviews.

If performance later requires denormalized rating statistics, consider adding fields such as:

```text

```

Do not introduce denormalization without a clear reason.

# 46. Inventory and Orders

Inventory operations must be transactional.

When an order is successfully placed:

1. Validate product availability.
2. Validate variant availability.
3. Reserve or decrement inventory.
4. Create the order.
5. Create order items.
6. Create the payment record.
7. Record inventory transactions.
8. Update order status.
9. Commit the transaction.

If any critical step fails, rollback the appropriate transaction.

Prevent overselling through proper PostgreSQL transactions and row-level locking where necessary.

   ↓

   ↓

   ↓

   ↓

Receive payment confirmation
   ↓
Confirm order
   ↓
Update inventory

Do not trust prices or totals submitted by the frontend.

The backend must calculate authoritative prices.

# 51. Important Architectural Constraint

Do NOT add Redis, MongoDB, Sanity, Elasticsearch, or another database to this PostgreSQL architecture unless there is a clearly justified requirement.

PostgreSQL should initially remain the primary and authoritative application database.

Redis, if introduced later, should be treated as a cache/session/performance layer and should not replace PostgreSQL as the source of truth for orders, payments, inventory, or customer business data.

Sanity, if introduced later, should be used for editorial/marketing content rather than replacing PostgreSQL's transactional commerce data.
